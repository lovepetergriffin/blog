Claude Code 自定义命令：Slash Commands 全解析

发布于 2026-10-24进阶Claude CodeSlash Commands自定义命令效率

Claude Code 的 Slash Commands 是最被低估的效率工具：你把重复的工作流写成一个命令，以后一个斜杠就搞定，不用每次重新描述需求。这篇讲内置命令、自定义命令怎么做、参数怎么传，以及自定义命令和 Skills 的区别。

跟你有啥关系：如果你发现自己总在给 Claude Code 重复同一段话——「检查一下这段改动」「给这个文件补测试」「部署前检查一遍」——那就是该写自定义命令的时候了。写一次，团队所有人都能用。

Claude Code Slash Commands 是什么

Slash Commands 就是在 Claude Code 会话里以 / 开头的快捷指令。输入 / 会弹出命令菜单，敲几个字母过滤，回车执行。

它分两类：

  • 内置命令：Claude Code 自带的，比如 /help、/clear、/review。
  • 自定义命令：你自己写的，放在 .claude/commands/ 目录下，一个文件就是一个命令。

原理很简单：自定义命令文件的内容就是一段提示词模板。你敲 /review，Claude Code 就把 review.md 里的提示词发给模型执行。没有特殊语法，写提示词的能力就是写命令的能力。

Claude Code 内置 Slash Commands 全表

跟你有啥关系：先把内置的用熟，再决定哪些值得写成自定义的。很多需求其实内置命令已经覆盖了，不用重复造轮子。

会话管理类

命令 干嘛
/help 看所有可用命令
/clear 清空对话，换新任务（CLAUDE.md 还在）
/compact 压缩上下文，省 token，长会话必备
/exit 或 /quit 退出 Claude Code
/status 看会话与认证状态
/model 切换模型
/config 看当前配置

代码操作类

命令 干嘛
/init 扫描项目，生成 CLAUDE.md
/diff 看当前 git 改动
/review 检查改动里的 bug
/commit 生成提交信息并提交
/pr 创建 Pull Request
/memory 查看/编辑 CLAUDE.md
/permissions 看当前工具权限
/agents 列出可用子 Agent

我试了一下，日常最常用的就五个：/clear、/compact、/diff、/review、/commit。会话一长就 /compact，任务一切换就 /clear，提交前一定 /diff + /review。

Claude Code 自定义命令怎么做

跟你有啥关系：这是本篇的核心，学会了，重复工作流就再也不用打字了。

第一步：建目录和文件

在项目根目录建 .claude/commands/，每个 .md 文件就是一个命令：

.claude/commands/review.md       →  /review
.claude/commands/add-tests.md    →  /add-tests
.claude/commands/deploy-check.md →  /deploy-check

文件名就是命令名，文件内容就是提示词。没有别的配置，不用注册，不用重启，保存完立刻能用。

第二步：写提示词模板

拿 /review 举例子，这是我一直在用的版本：

<!-- .claude/commands/review.md -->
检查当前改动。
检查项：
- 改动里有没有 leftover 的 debug 输出、注释掉的代码
- 有没有半截重命名（改了定义没改调用）
- 有没有被偷偷删掉或弱化的测试
- 有没有碰 secrets、鉴权、配置文件

输出编号列表，文件:行号。只说问题，别夸代码。

敲 /review，Claude Code 就会按这个模板执行。固定检查清单比每次随口问「这段改动有没有问题」靠谱得多——同样的问题每次都查，不会漏。

第三步：用 $ARGUMENTS 传参数

跟你有啥关系：没有参数的命令只能干固定活，有了参数，一个命令能覆盖一类任务。

$ARGUMENTS 是占位符，调用时跟在命令后面的内容会填进去：

<!-- .claude/commands/add-tests.md -->
给 $ARGUMENTS 补测试。
用 Vitest。覆盖正常路径 + 一个边界情况 + 一个异常情况。
测行为不测实现，跟现有测试风格保持一致。

调用时：

/add-tests src/lib/stripe/webhooks.ts

$ARGUMENTS 就被替换成 src/lib/stripe/webhooks.ts。一个命令，全项目通用。

第四步：限制工具范围，更安全

跟你有啥关系：有些命令只应该读、不应该改，比如 review。限制住工具，它就没法在你眼皮底下悄悄「顺手修掉」。

在文件开头加 front matter：

---
description: 提交前检查暂存区改动
allowed-tools: Bash(git diff:*), Bash(git status:*)
---

跑 `git diff --staged`，只看暂存区的改动。
按这个顺序报告：
1. leftover 的 debug 输出、注释代码、新增的 TODO
2. 没改全的重命名或签名变化
3. 被跳过、删除、弱化的测试
4. 碰 secrets、鉴权、配置文件的改动
不要改文件。最后说"可以提交"或者列出要修的项。

allowed-tools 只列了两个只读 git 命令，这个 review 命令就只能看不能改。你决定改什么，改完再跑一次 /review 确认。

第五步：提交进 git，全团队共享

.claude/commands/ 提交进仓库，团队所有人 checkout 之后自动获得同一套命令。跟 CLAUDE.md 一样，这是团队资产，不是个人配置。

我的建议：先把团队最常重复的三件事写成命令——review、补测试、部署检查——跑顺了再慢慢加。命令不在多，在每次都用得上。

Claude Code 自定义命令实战例子

跟你有啥关系：光讲原理不够，直接抄这几个，改改就能用。

部署前检查：/deploy-check

我们马上要部署到生产。
把所有你觉得现在不应该发的东西标出来。
每个问题一句话，最严重的放最前面。
如果没问题，只说"可以部署"，别多说。

部署前敲一下，等于多了一道人工检查关。

安全审计：/security

对 $ARGUMENTS 做安全审计。
检查：缺鉴权、没验 ownership、没校验的输入、暴露的 secrets。
只列问题，别夸。

调用：/security src/routes/payment.ts

提交信息：/commit-msg

给暂存区的改动写提交信息。
祈使句，不超过 72 个字符。说清楚改了什么和为什么。
只输出信息本身，不要真的提交。

注意跟内置 /commit 的区别：内置的是直接提交，这个是只生成信息、让你过目再决定，适合提交信息有团队规范的场景。

上下文瘦身：配合 /compact 使用

自定义命令不是万能的，长会话里上下文一满，命令再好也救不了「失忆」。我的节奏：

  • 20-30 轮对话后跑一次 /compact
  • 换任务跑 /clear
  • 高价值约定用 # 开头写进 CLAUDE.md，别只留在对话里

Claude Code 自定义命令和 Skills 的区别

跟你有啥关系：这两个容易搞混，选错地方写，命令要么调不出来，要么触发时机不对。

维度 自定义命令（.claude/commands/） Skills（.claude/skills/）
触发方式 你手动敲 /命令名 你敲 /技能名，或模型按需自动调用
文件形式 单个 .md 文件，内容就是提示词 目录 + SKILL.md，带 front matter（name、description、argument-hint、user-invocable）
适用场景 固定流程，你明确知道要干嘛 专项能力，让模型在合适的时候自己决定用不用
参数 $ARGUMENTS $0、$1 等位置参数

举个例子：

  • /review、/deploy-check 这种「你每次都想主动执行」的，写自定义命令。
  • 「部署应用」这种「步骤多、模型可能需要自己判断什么时候用」的，写 Skill：
---
name: deploy
description: 部署应用到生产环境
argument-hint: "[环境]"
user-invocable: true
---

部署应用到 $0 环境（默认 staging）。
步骤：
1. 跑测试套件
2. 构建生产包
3. 用部署脚本部署
4. 检查部署健康状态

调用：/deploy production。

简单记：主动执行的写命令，模型按需调用的写 Skill。两个都放在项目里，都能进 git 共享。

Claude Code 自定义命令避坑清单

跟你有啥关系：这几个坑踩过一次就长记性，提前避开省时间。

  1. 命令名别跟内置的撞。你写了个 review.md，它会覆盖内置 /review，团队有人按内置行为预期用就会懵。要么换个名字（比如 /my-review），要么确认全团队都知道你改了它。
  2. 提示词别写太长。命令文件是每次调用都全量塞进上下文的，写 200 行模板等于每次多花 200 行 token。精简到能说清检查项和输出格式就行。
  3. $ARGUMENTS 为空时要有默认行为。比如 add-tests 没给文件时，是报错还是让模型先问你？模板里写一句「如果没给文件，先问我要补哪个文件」。
  4. 别在命令里放敏感信息。命令文件是要进 git 的，token、内网地址、客户名都别往里写。
  5. 定期清理没人用的命令。命令一多，/ 菜单翻半天找不到要用的，比没有还烦。季度清理一次，只留每周都用的。

我的 verdict

Claude Code 自定义命令的价值就一句话：把重复说的话变成一个词。review、补测试、部署检查、安全审计，这些你每周都要说好几遍的话，写成命令后就是一次敲击的事。

先写三个：/review、/add-tests、/deploy-check，跑一周，感受一下每天省下来的打字和返工，再决定要不要继续加。命令的 ROI 来得很快，因为成本只是一次写模板的时间，收益是每次调用都省。

命令与功能截至 2026 年 10 月撰写时，以 Claude Code 官方文档为准，版本更新后个别行为可能有变。
