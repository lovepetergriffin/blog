Codex Agent 模式：让 AI 自主完成多文件重构

发布于 2026-10-24进阶CodexAgent重构多文件OpenAI

Codex Agent 模式不是聊天框，是一个能自主干活的工程师：你丢一个目标，它自己读仓库、定方案、跨文件改、跑测试，改完交 diff 给你。这篇讲 Agent 模式怎么用、多文件重构的实战流程，以及怎么 review、怎么设安全边界。

跟你有啥关系：单文件小改动用补全就够了，但「把 A 模块的调用方式全换成 B」「抽一个公共组件出来，20 个文件都要改」这种跨文件活，手动改一下午还容易漏，Agent 模式就是为这种活生的。

Codex Agent 模式是什么

Codex 有两种工作形态，很多人混着用，效果大打折扣：

形态 命令 特点
交互模式（Agent） codex 持续会话，上下文一直都在，能连续干多件事
非交互模式 codex exec "任务" 跑完一个任务就退出，适合脚本和 CI

Agent 模式的核心是交互模式：你进一个会话，Codex 在这个会话里记住项目结构、记住你前面说过的约定，一件事接着一件事干。上一轮刚重构完支付模块，下一轮你说「按刚才那个方式把退款模块也改了」，它不用重新问你「刚才那个方式是什么」。

还有一种云端 Agent：你在网页或 ChatGPT 里提交任务，Codex 把仓库克隆到隔离的云沙箱里，改完、跑完测试、直接给你一个 PR，你不用开本地终端。这种适合「丢过去、过会儿回来收 PR」的场景，跟本地 CLI 互补，不冲突。

一句话区分：交互模式是雇了个同事坐你旁边，非交互模式是派了个跑腿的出去办事。多文件重构这种需要上下文、需要来回商量的活，一定用交互模式。

Codex Agent 模式怎么用：开局五连

跟你有啥关系：Agent 自主干活的前提是它先认识你的项目，不做开局配置，它就是个没看过说明书的新人。

进项目目录，启动 Codex，依次跑：

/init
/permissions
/mcp
/skills
/hooks
  • /init：生成 AGENTS.md，Codex 的项目记忆文件。生成后自己改改，补上：项目结构、常用命令、代码规范、哪些目录不能碰。
  • /permissions：设审批策略。重构这种要大面积写文件的活，建议先用「写文件前确认」，跑顺了再放开。
  • /mcp、/skills、/hooks：看一眼接了哪些工具、技能、钩子，心里有数。

AGENTS.md 写什么，直接决定 Agent 的下限。我用的模板：

# 项目名：一句话说清干嘛的

## 结构
- src/services/ — 业务逻辑
- src/routes/ — 接口层
- src/lib/ — 公共工具

## 命令
- 跑测试：npm test
- 启动：npm run dev
- 检查类型：npm run typecheck

## 规范
- 重构时保持公开接口不变，除非明确说了要改接口
- 每个改动的文件都要有测试覆盖
- 不要动 src/legacy/ 下的代码，那是历史遗留

「不要动 legacy」这种话一定要写进 AGENTS.md，光在对话里说一次，Agent 跑长了就忘了。

Codex 多文件重构实战流程

跟你有啥关系：流程对了，重构一次成；流程错了，Agent 改到一半跑偏，你还得花时间擦屁股。

我固定用五步法：

第一步：让 Agent 先看，再定方案

不要一上来就说「开始重构」。先让它看：

先看一下 src/services/payment/ 和 src/services/refund/ 的结构，告诉我这两个模块现在是怎么互相调用的，不要改代码。

Agent 只读不写，把现状摸清楚。这一步的输出就是你后面 review 方案的依据。

第二步：定方案，明确边界

方案：把 payment 和 refund 里重复的校验逻辑抽成 src/lib/validate.ts，两个模块都改成调它。公开接口不变，legacy 目录不动。先给我方案，确认了我再让你动手。

关键点：

  • 抽什么、放哪、谁来调，三个说清楚。
  • 边界：公开接口变不变、哪些目录不动、测试要不要补。
  • 先给方案再动手：方案你点头了它再改，比改完再返工便宜得多。

第三步：分批改，别一次全改

20 个文件的重构，别让 Agent 一口气全改完。分批：

先改 payment 模块的 3 个文件，改完跑测试，通过了再继续 refund 模块。

一批 3-5 个文件，改完验证通过再下一批。Agent 跑偏了也只偏一批，纠错成本小。我试了一下，一次改 20 个文件，中间出个错，定位都费劲；分批改，出错立刻知道是哪一批。

第四步：让 Agent 自己跑测试

任务描述里直接写验证要求：

每批改完跑 npm test，全部通过才算这批完成。失败了自己看报错修，不要跳过测试。

Agent 自己跑测试、看报错、修代码、再跑，形成闭环。你不用当监工，只需要最后看 diff。

第五步：逐批 review，不要攒到最后

每批改完就看 diff，不要等 20 个文件全改完再一次性 review：

/diff
/review

/diff 看改了什么，/review 让 Agent 从审稿人视角再审一遍：接口是不是真没变、有没有漏掉的调用点、有没有被顺手删掉的测试。批批都干净，最后合起来才干净。

Codex Agent 模式 Review 策略

跟你有啥关系：Agent 交出来的 diff，你不 review 就合并，等于把代码质量押在它一次输出上。Review 不是不信任，是流程的一部分。

三层 review，层层过滤

第一层：Agent 自审。改完跑 /review，让它自己先过一遍。能拦住 leftover debug、半截重命名、被删的测试这些低级问题。

第二层：你审 diff。重点看四样：

  1. 公开接口是不是真没变（说了不变就不能变）。
  2. 所有调用点是不是都改到了（重构最怕漏一个）。
  3. 有没有动不该动的目录（AGENTS.md 里写了不动的，有没有真不动）。
  4. 测试是不是真覆盖了改动（不是只改了代码没补测试）。

第三层：CI 兜底。测试、类型检查、lint 全跑一遍，挂了就打回。Agent 的改动也要过 CI，没有例外。

任务模板：直接抄

下次重构，直接套这个模板，省掉每次重新描述的功夫：

重构任务：

现状：

方案：
- 抽什么：
- 放哪：
- 谁来调：

边界：
- 公开接口不变
- 不动 src/legacy/
- 每个改动文件补测试

执行方式：
- 分批改，每批 3-5 个文件
- 每批改完跑 npm test，通过再继续
- 每批改完我先 review，再下一批

模板的价值是把「方案、边界、执行方式」一次说清，Agent 不用猜，猜错的成本也就没了。

Codex Agent 模式安全注意事项

跟你有啥关系：Agent 能写文件、能跑命令，权限给错了，破坏力跟能力成正比。

  1. 权限分级。个人项目可以放开，团队仓库默认审批，生产相关仓库先从只读起步。/permissions 里设，别图省事全开 Auto。
  2. 沙箱不能省。Codex 的沙箱是把 Agent 的操作关在项目目录里，命令行启动可以用 --sandbox 指定级别。别为了图快关掉沙箱。
  3. secrets 别进对话。API Key、数据库密码、内网地址，不要贴进 Codex 会话。会话记录可能被保存，贴进去等于留了个副本。
  4. 大面积删除要人工确认。重构里凡是涉及删文件、删大段代码的，提前说「删除前先列出来我确认」，别让 Agent 自行决定删什么。
  5. 云端 Agent 的 PR 也要 review。云端交回来的 PR 跟本地改的同等对待，三层 review 一步不能少。PR 描述写得再漂亮，diff 还是要自己看。

一句话：Agent 的能力越大，边界就要划得越清楚。边界写在 AGENTS.md 里、写在任务模板里，比事后擦屁股便宜得多。

我的 verdict

Codex Agent 模式值不值得用来做多文件重构？值得，但前提是流程对：先看再定方案、分批改、每批自验证加 review、权限按仓库分级。

最忌讳的用法是丢一句「把这堆代码重构一下」然后去喝咖啡，回来收一个 20 文件的 diff，review 到眼睛花。Agent 不是替你 review 的，它是替你干活的，review 永远是你的活。

记住一个公式：好方案 + 清边界 + 分批验证 = 一次成的重构。三个缺一个，返工概率就翻倍。

命令与功能截至 2026 年 10 月撰写时，以 OpenAI Codex 官方文档为准，版本更新后个别行为可能有变。
