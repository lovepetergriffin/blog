Claude 提示词工程：怎么写才能让它输出直接能跑的代码

发布于 2026-10-24进阶Claude提示词AI 编程技巧

同样是 Claude，有人一句话就拿到能跑的代码，有人来回十轮还在改 bug。差的不是模型，是提示词。

跟你有啥关系：提示词写得好，Claude 第一次输出就能用；写得差，你花在修 bug 上的时间比自己写还多。这篇讲五个能立刻上手的技巧，个个有正反例子。

Claude 提示词技巧：动词开头，说清楚你要什么

跟你有啥关系：Claude 不会猜你的意图，你含糊，它就含糊。

Anthropic 官方的建议就一句话：用直接的动作动词开头，说清楚你要的输出，而不是只说话题。

❌ 差的说法：

帮我看看这个 JD

Claude 不知道你要它干嘛：重写？翻译？挑毛病？它只能猜一个。

✅ 好的说法：

审查这份 JD，用三个要点标出过时的表述，每个要点不超过 15 个字。

动词（审查）+ 输出形式（三个要点）+ 约束（每点 15 字内），三要素齐了，Claude 不用猜。

代码场景同理：

❌「修一下这段代码」 ✅「重构这段 Python 代码，提高可读性，遵守 PEP 8，不要改函数签名，改完附上改动说明」

我试了一下，动词开头这个习惯养成后，第一轮输出的可用率明显上升。不是模型变聪明了，是你终于把话说清楚了。

Claude 提示词技巧：给上下文，还要讲清楚为什么

跟你有啥关系：上下文决定 Claude 的判断力，不给上下文，它只能按通用情况写，放到你的项目里大概率水土不服。

给上下文不是贴一堆代码就行，还要讲清楚这个输出是给谁用的、用来干嘛的。因为用途决定了 Claude 在格式、深度、取舍上的判断。

❌ 差的说法：

用通俗的语言写

通俗给谁看？给刚入行的新手，还是给非技术的老板？两种「通俗」完全不一样。

✅ 好的说法：

用通俗的语言写，这份文档是给一线组长看的，他们不是 HR 专业出身，别用人力资源术语。

代码场景：

❌「写一个分页接口」 ✅「给 /api/todos 加分页，参数 page 和 page_size，照着 routes/users.py 已有的分页写法来，返回里带 total 字段。这个接口是给前端列表页用的，前端已经按这个格式在解析了，别改字段名。」

最后一句「别改字段名」就是「为什么」——因为前端已经在按这个格式解析，改了就崩。Claude 知道了原因，就不会自作主张「优化」字段名。

Claude 提示词技巧：格式先定好，别让它自由发挥

跟你有啥关系：不指定格式，Claude 会自己选一个，而它选的往往不是你要的。

❌「总结一下这篇文章」 ✅「用三个要点总结，每点不超过 15 个字」

代码场景，格式要求要具体到能直接用的程度：

输出一个 Python 函数，函数名 fetch_user_orders，参数 user_id（int）和 limit（int，默认 20），返回 list[dict]，每个 dict 里有 order_id、total、created_at 三个键。用标准库 + requests，不要引别的依赖。函数前面加 docstring，说明参数和返回值。

版本、依赖、函数签名、返回结构，全定死。Claude 照着填空就行，填空题总比作文题得分高。

还有个细节：说要什么，不要说不要什么。Claude 对否定指令的执行不太稳。

❌「不要用 markdown」 ✅「输出用纯段落，不要列表」

正向描述永远比否定描述可靠，这是 OpenAI 和 Anthropic 两边都提过的共识。

Claude 提示词技巧：示例胜过千言万语

跟你有啥关系：有些东西（风格、语气、格式）用语言描述半天说不清，贴一个例子立刻就懂。

Few-shot 提示就是这个道理：给一个例子，Claude 照着学。

一个例子（one-shot）通常就够了，只有输出还是不对时再加第二个。例子不是越多越好，例子之间风格不一致反而会把 Claude 搞糊涂。

我试了一下，代码风格这个场景，示例的效果尤其明显：

  • 你说「写得简洁一点」，Claude 理解的简洁和你理解的简洁可能差很远。
  • 你贴一段你项目里公认写得好的代码说「照这个风格」，它立刻就能对齐命名、注释密度、错误处理方式。

输入输出示例也一样重要。让 Claude 生成代码时，直接给它输入输出对：

输入：{"user_id": 123, "items": [{"sku": "A1", "qty": 2}]} 期望输出：{"order_id": "ORD-2026-0001", "total": 99.0} 按这个契约实现 create_order 函数。

有契约在，Claude 生成的代码第一次跑通的概率高得多。

Claude 提示词技巧：小步迭代，别指望一发入魂

跟你有啥关系：第一次输出不完美是常态，迭代 2-3 轮后质量会明显上一个台阶。指望一发入魂，等于放弃了 Claude 最擅长的迭代能力。

我的固定流程：

第一轮：给骨架，让它跑起来

实现一个 FastAPI 的健康检查接口 /health，返回 {"status": "ok"}。只用标准库和 FastAPI，不要别的依赖。

先拿到能跑的最小版本，别在第一轮就塞十个需求。

第二轮：贴真实报错，让它修

代码跑不起来时，别只说「报错了」，把真实报错原样贴回去：

跑起来报这个错：

Traceback (most recent call last): File "main.py", line 42, in <module> ... ModuleNotFoundError: No module named 'xxx'

只改最小的地方修掉它，不要重构整个文件。

贴真实报错 + 要求最小改动，这是调试场景最有效的组合。Claude 看到真实堆栈，定位比你自己描述「好像是导入问题」准得多。

第三轮：加约束，收紧输出

现在加两个约束：第一，只用标准库，除非必要不要引新依赖；第二，补一个测试，覆盖正常和异常两种情况。

约束要一轮一轮加，别第一轮就全加上。第一轮约束太多，Claude 会为了满足所有约束把代码写得四不像；先跑起来，再收紧。

还有两个配套习惯：

  • 让它自己验证：任务描述里直接写「改完跑 pytest，全部通过才算完」。Claude 自己跑测试、看报错、修代码，形成闭环。
  • 允许它说不知道：提示词里加一句「如果信息不足以得出结论，直接说不知道，不要猜」。Claude 默认倾向于给一个答案而不是承认不确定，这句话能显著减少一本正经的幻觉。

我的 verdict

提示词工程没有玄学，就五句话：

  1. 动词开头，说清楚你要什么输出。
  2. 上下文加原因，让 Claude 知道为谁而写、为什么。
  3. 格式先定死，用正向描述，别用否定。
  4. 示例胜过描述，风格和契约贴出来。
  5. 小步迭代，先跑起来再收紧，报错原样贴回去。

记住一个底线：Claude 不是读心术士，它是你手下最能干但也最需要明确指令的工程师。指令越明确，它回馈你的质量越高。反过来，你含糊，它就只能猜，而猜错的成本最后都算在你头上。
